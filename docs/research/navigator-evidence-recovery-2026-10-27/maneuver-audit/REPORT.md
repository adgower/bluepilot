# Saved original maneuver evidence recovery

Started 2026-10-27; continued 2026-10-28. Local, read-only evidence work. No controller changes, replay, device contact, CAN transmission, or changes to the paired source or owner factors.

## Scope and data quality

The first pass covered the frozen lateral corpus: 42 routes / 737 unique compressed original files. That corpus alone was insufficient to answer whether saved maneuver experiments existed. The longitudinal 23-route / 316-file manifest added 216 originals after 100 exact compressed-SHA overlaps; the earlier 96-file OEM/Alpha lineage added 35 OEM originals, with its 61 Alpha files already represented. That produced 988 unique originals.

Reconstructing the acquisition registry used only `input-manifest.json` files whose sibling acquisition receipts explicitly report `segment_hashes_verified:true`. The registry contains 1,154 unique original compressed hashes, overlapping the initial 988-file union in 473 files. Therefore 681 registry files required a further metadata pass, while 515 legacy corpus files fall outside this receipt convention. The final bounded union is 1,669 originals; it is not a claim that every archive anywhere has been exhausted. Generic session aliases are not raw recording identities and were not used for hash deduplication.

All 681 additional registry originals resolved by expected SHA and byte size without copying or unpacking. Empty normalized alias directories accounted for 301 files; their originals remained under the six identified acquisition `original/` roots. This was a path-resolution issue, not lost evidence. The first 737-file receipt remains separate and inspectable.

The completed union has 127 drive-alias/source-commit groups and 192,928 manager publications per maneuver daemon. No lateral daemon is running in any observed sample and no lateral maneuver plan is retained. Forty-two init snapshots explicitly have lateral mode disabled; 1,627 omit that parameter. Two historical longitudinal-tool sessions supply the 4,843 running longitudinal-daemon observations. All 26 recorded parent git objects needed for interpreting tool/process definitions are available; historical dirty working trees still cannot be reconstructed exactly from a parent commit alone.

## Marker semantics

Historical source objects and hashes are recorded separately from current source. `LongitudinalManeuverMode` starts `maneuversd` and suppresses `plannerd`; `LateralManeuverMode` starts `lateral_maneuversd`. Daemon running, an enabled parameter snapshot, an active plan/alert, and completion are separate evidence dimensions. Missing parameters remain unknown. Not-running manager samples describe their own observation times, with startup, publication gaps, and unlogged runtime parameter changes left explicit.

The lateral tool automatically executes its action suite after readiness; the driver manually selects ACC speed. Code requires two seconds of readiness, whereas its README says one. Valid `lateralManeuverPlan` identifies active actions. Its standard 20/30-mph suite does not directly establish 35–50-mph steering response. The longitudinal tool begins after engagement and initial-speed readiness, publishes the commanded acceleration sequence through `longitudinalPlan`, and reports phases through `alertDebug`. Alerts alone do not prove actuator ownership.

The lateral-only first pass had 85,827 manager samples per maneuver daemon, zero running/should-running samples, zero `lateralManeuverPlan` messages, and zero `alertDebug` messages. Its 737 init snapshots omitted mode parameters. A supplemental examination of 124,785 log/error messages found 113 literal maneuver mentions: 29 logger subscription announcements and 84 missing/not-alive-topic diagnostics. Those are not maneuver execution markers.

## Recovered genuine longitudinal experiment

`maneuver-followup-session-06`, outside the initial lateral corpus, has 20 original segments with explicit longitudinal mode enabled, lateral/joystick modes disabled, running `maneuversd`, active phase alerts, and a finished marker. Recorded parent source is clean `ead00c30e0f3e174130f475847b1f4a2a76e8902`; the acquisition binds child `d4a201251d184a446cb2db383f4bd024c93e75cb`. This is historical tuning, not current installed-source validation.

The additional verified-acquisition pass also finds `maneuver-session-05` (22 originals, clean parent `74eaa6a60d344f141d06da16f4dbe10d3de49c0e`, child gitlink `3a5fe9fe5a296d44b7f898b580c2d3afafe6bfd1`) with explicit longitudinal mode enabled, lateral/joystick disabled, running longitudinal daemon and suppressed planner. Its separate targeted extraction recovers 26 active phases: three stops, three starts, 18 creep actions and two −1 m/s² brake steps. All 5,680 commands within these markers are enabled; 25 phases have no observed driver/quality/mismatch flags. It has no finished marker or later strong-brake/gas suite completion. This second historical source cohort remains separately labelled rather than silently pooled with the 20-file result below.

The targeted extraction contains original outgoing ACCDATA (DBC decimal address 390, hexadecimal 0x186), original received brake/torque/status messages, carState, carControl, and contiguous alert phases. It contains no simulated reference commands. CarParams reports openpilot longitudinal ownership; actual outgoing enable bits and `carControl.longActive` confirm execution rather than merely an enabled tool.

There are 36 active phases: three stop trials, three starts, 18 alternating creep actions, and three repeats each of −1, −3.5, +1, and +2 m/s² step sequences. The three nominal −0.5 m/s² stop phases span 11.95–12.00 seconds, and the six braking step phases span about 2.95–3.00 seconds. All nine braking phases have enabled outgoing commands, active longitudinal control, and no observed gas/brake/steering override, invalid CAN, or vehicle-sensor-invalid samples. Other phases include pedal overrides and cannot be pooled without screening.

These are controlled **planner acceleration** sequences, not constant actuator steps. In the −0.5 stop trials, actual requested brake acceleration spans approximately −2.61 to +0.0733 m/s² as the existing controller and stopping behavior operate. This is useful repeated excitation, but does not by itself identify an open-loop actuator model or the incremental effect of a proposed allocator.

The ten-second post-braking screens expose eight first brake-bit clearances approximately 0.061–0.255 seconds after the last active alert. The third stop trial continues braking throughout that screen. One −1 release window includes brake/steering override and loss of longitudinal activity. Most clean windows promptly enter positive setup requests up to approximately +2 m/s²; these are not isolated weak-positive coast windows. Original RX torque/status and exact command prefixes are retained for a separate conditional response assessment.

## Evidence limits and artifacts

`controlled-longitudinal-original.npz` and its JSON schema/hash receipt preserve 57,124 original outgoing ACCDATA packets, 114,855 carState publications, 114,346 carControl publications, and 57,664 received samples each for brake torque and brake-status channels. Event clocks are recorded publication/send/receive times, not ECU internal measurement timestamps. Repeated marker first/last ranges must not be mistaken for continuous plateaus; `alert_phases` contains the actual contiguous phase sequence.

The separate `second-controlled-longitudinal-original` files preserve the earlier 22-file cohort. `followup-phase-context` and `earlier-phase-context` retain controlsState post-update state/PID components and the exact consumed `longitudinalPlanMonoTime`, plan `shouldStop` and acceleration target, carControl actuator pre-update state, and observed controlsMismatch events. Both historical sources assign actuator state before the longitudinal update and controlsState state after it; those values must not be assumed identical. Exact plan-clock matching confirms the −0.5 stop sequences mix PID and stopping modes, whereas the recovered −1 braking steps are PID with `shouldStop:false`. Decoder message-block hashes for all seven selected ACC/brake/torque/gear channels match both historical children and the actual decoder used. No controlsMismatch events occur within the recovered active marker intervals; this is a recorded-event statement, not a continuous physical fault guarantee.

`FINAL_INVENTORY.json` is the bounded union classification; `segments.jsonl`, `additional-segments.jsonl`, and `registry-additional-segments.jsonl` retain per-original hashes, timing coverage, process observations, selected mode snapshots, and source/tuning metadata. `all-historical-source-availability.json` distinguishes available git objects from dirty runtime source guarantees. `controlled-phase-audit.json` and `release-window-screen.json` preserve screening results. No model validity, physical calibration, current-controller benefit, or permission to activate a change follows from this audit.
