## Recommended order and tradeoffs

| Order / roadmap | Candidate | Benefit to Alex | Cost / limitation / next gate |
| --- | --- | --- | --- |
| **Now: NAV-01** | Finish the bounded tracking experiment; study genuine post-override stalls separately | Addresses the actual persistent ~15 mph complaint | Replay now passes; physical benefit and stability unknown. Do not combine a steering-release pulse, smoothing and gain calibration into the same trial |
| **Alongside NAV-01: NAV-15** | Read-only steering diagnostics: requested vs measured curvature, EPS status, active limits, valid delay estimate, build/settings identity | Explains weak steering and makes comparisons far less dependent on memory; high value for modest scope | Port data semantics into vanilla architecture; missing/stale data must show unknown, not a reassuring number. Start with offline report, then unobtrusive UI |
| **NAV-02** | Reproducible updates, rollback and regression replay with preserved calibration | Restores maintainability after the earlier dirty-checkout/update failure | Keep pause until the fork's own update/build path is verified; model download retry alone does not fix Git checkout errors |
| **Next functional work: NAV-03, or NAV-04 if manual speed is preferred** | Ford longitudinal coordination; independent steering/cruise engagement | Longitudinal addresses highway complaint; MADS offers lane centering while Alex controls speed | Both need their own integration and road evidence. MADS requires matching state machine, buttons, UI, brake/fault/cancel semantics and Panda authorization |
| **Later: NAV-05/06** | Input-side anti-weave and recommendation-only calibration | Could improve straight-road comfort and tune supported speed bands | Smoothing can add lag; auto calibration has admission/mapping mismatch with the custom trial. Do not overwrite 1.20/0.97 or mask low-speed authority limits |
| **Later: NAV-16** | Separate camera reset from learned steering-delay/vehicle/torque resets | Preserves useful learning during model/calibration maintenance | First audit current upstream reset behavior. Provide explicit offroad choices; a real bad calibration must still be reset deliberately |
| **Later: NAV-17** | Compatible model packages and resilient cached downloads | Useful if model experimentation becomes a goal | Requires model/parser/tinygrad/warp/Chestnut compatibility as one tested unit. Current big model is already working; broad selector port has lower immediate yield |

This is qualitative WSJF: steering and diagnostics reduce the highest current uncertainty; longitudinal/MADS offer the next large everyday benefit. Theme packs, bulk model switching and different-car tunes have lower expected yield now.

## The most relevant BluePilot open work

**Low-speed stall rescue, not continuous gain feedback:** [#153](https://github.com/BluePilotDev/bluepilot/pull/153), open, extends an existing post-override release pulse from above 9 m/s down to **5 m/s (~11.2 mph)** when pinion measurement is enabled. Its [diff](https://github.com/BluePilotDev/bluepilot/pull/153/changes) changes gate/charging logic in `lateral_angle_ext.py`; it depends on a stall detector and pulse mechanism absent from this vanilla port. A 300 ms mode-0 release is materially different from this task's bounded tracking term.

The author explicitly says to land [#148](https://github.com/BluePilotDev/bluepilot/pull/148), also open, first: the fractional-delivery guard aims to avoid releasing steering during ordinary delayed curve entry. Exact-tip road evidence remains limited in #153, and its own description says pulses cannot repair every low-speed EPS authority limit. The author's route results are not independent Navigator evidence. **Action: label our saved deficits as pre/post-override, transient/persistent and EPS-limited before considering a separate local stall-rescue experiment.** No pulse was added now.

**EPS telemetry:** [#155](https://github.com/BluePilotDev/bluepilot/pull/155), open, adds optional status parsing and hands-on context. Its reported ~25 mph availability boundary concerns the author's Q3 CAN platform. The original survey's `[2,0,2]` Navigator tuple covered control state, limit and capability, not the separate availability field. The subsequent [saved-drive comparison](navigator-stall-rescue-comparison-2026-10-14/REPORT.md) directly decodes availability0 in all selected weak-turn windows and a strong speed-linked pattern near25mph on this CAN-FD Navigator itself. This is now a local clue, while physical authority and causation remain unproven. Use noncritical, seen/stale-aware telemetry first. Suppressing steer-saturated alerts is not recommended as a steering fix.

**Prediction timing:** [#213](https://github.com/BluePilotDev/bluepilot/pull/213), open, reports benefit from speed-scaled prediction lookup on a 2025 F-150 Lightning. It changes **curvature-mode `LateralCurvExt`** and its predicted-curvature blend. Our angle conversion does not use that same path. Useful design hypothesis for timing research; not a direct patch for this Navigator and not grounds for adding a global delay.

**Lane position/takeover guards:** [#194](https://github.com/BluePilotDev/bluepilot/pull/194), **open draft**, includes lane-budget, stall and press-chatter changes, plus a pinion-aware deviation band. This is a multi-mechanism package; its proposed band is not the current port's unchanged ±0.002. Do not import it wholesale or widen safety bounds to get acceptance.

**Calibration and smoothing:** [#161](https://github.com/BluePilotDev/bluepilot/pull/161) is the auto-calibration proposal; [#172](https://github.com/BluePilotDev/bluepilot/pull/172) supplies its gauges. Both are open. [#171](https://github.com/BluePilotDev/bluepilot/pull/171), open and stacked on #161, describes input/gain-schedule smoothing and warns its removed output filter degraded a closed-loop rig. This favors isolated input-side evaluation, not indiscriminate output damping. [#180](https://github.com/BluePilotDev/bluepilot/pull/180), open, displays learned delay on Comma 4's compact tuning UI; [#175](https://github.com/BluePilotDev/bluepilot/pull/175) covers an uncalculated-delay indicator. These support NAV-15, not automatic changing of delay.

**Storage and startup:** [#215](https://github.com/BluePilotDev/bluepilot/pull/215), **open draft**, fixes legacy date-named recording retention ordering. Worth auditing during NAV-02 only if both naming formats and the vulnerable sorting helper exist in our current tree. It cannot recover deleted files. [#170](https://github.com/BluePilotDev/bluepilot/pull/170), open, is a useful radar-bus diagnostic concept if adapted to actual Navigator topology. [#209](https://github.com/BluePilotDev/bluepilot/pull/209) and [#210](https://github.com/BluePilotDev/bluepilot/pull/210) are portal power-save/onroad fixes: low direct value without that portal subsystem.

**Lower relevance:** [#212](https://github.com/BluePilotDev/bluepilot/pull/212) targets EV regen/brake behavior, not this gasoline Navigator's coordination problem. [#197](https://github.com/BluePilotDev/bluepilot/pull/197) is a theme pack. Neither outranks current control work.

## bp-exp README: useful pieces, incompatible bundle assumptions

The [README](https://github.com/dustin-decker/bluepilot/blob/bp-exp/README.md) credits calibration/smoothing/gauges and lane guards to the PRs above. New ideas worth retaining are separate camera-versus-steering resets, visible delay/evidence gauges, cached downloads that survive interruptions, and explicit parser/model compatibility checks. Its [download reliability commit ea983de7856bbc573c1e4febfcc0b108da0819a2](https://github.com/dustin-decker/bluepilot/commit/ea983de7856bbc573c1e4febfcc0b108da0819a2) retries transfer failures while reusing only verified chunks; this belongs to its sunnypilot model manager, not our source updater.

Crucially, the README says **USB-GPU/Chestnut remains gated off pending hardware validation**. Switching wholesale to bp-exp would not preserve the foundation this project was built to achieve. Its current README also says the removed retune's calibration evidence is incompatible and manual values are not automatically converted. Preserve our exact map and evidence rather than adopting its learned factors.

BluePilot [#214](https://github.com/BluePilotDev/bluepilot/pull/214) is an **open draft targeting bp-Lebowski**, not bp-dev. It documents a big-model runtime port with unresolved artifacts/tinygrad/OS integration choices. Our installed upstream-derived AGNOS 19.9/Chestnut path already works; its hybrid-OS example is not a recommended downgrade/migration plan.

## sunnypilot and StarPilot ideas

Sunnypilot's [16322aef167fe14de8af28a9e437101ed3c4dac5](https://github.com/sunnypilot/sunnypilot/commit/16322aef167fe14de8af28a9e437101ed3c4dac5) adds per-model tinygrad provenance, and latest [9bebe42f735e8859421ca3cfcb2f57377bb1f954](https://github.com/sunnypilot/sunnypilot/commit/9bebe42f735e8859421ca3cfcb2f57377bb1f954) fixes default big-model build/warp artifacts. These are packaging/build compatibility ideas, not evidence a different model would steer the Navigator better. NAV-17 should pin compatible model/parser/compiler/warp revisions together and retain the known-good package.

StarPilot's visible commits offer particularly useful **verification patterns** for NAV-02/NAV-04: [AOL state-machine fixtures 1590a5c](https://github.com/firestar5683/StarPilot/commit/1590a5cc2ba9724bb6cee5375c3b4451192d2dd1), [AOL defaults OFF e47133b](https://github.com/firestar5683/StarPilot/commit/e47133be1aa58d66a2ea10eae5ad345001800533), and [controller/native safety audit e6390c3](https://github.com/firestar5683/StarPilot/commit/e6390c32e122b1ebf02436f8c6210734018f4ede). The fixture file explicitly says synthetic state tests do not model physical buttons, CAN safety or actuation. Adopt that distinction; do not infer universal Ford MADS support from fixture counts. UI batching/settings caching may help if measured UI lag appears, but current road logs do not show model frame drops. Other-brand pedal/tune commits do not address this Navigator.

## Decision

Keep the current local bounded tracking work as NAV-01. Add diagnostics, deliberate calibration resets and compatible model-package research as NAV-15–17; fold storage/replay ideas into NAV-02 and AOL/button tests into NAV-04. Keep low-speed pulse rescue as a separately gated NAV-01 research alternative. Do not deploy a fork switch or combine new behavior changes on the basis of this survey.
